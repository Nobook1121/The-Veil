# 单页应用（SPA）迁移多页面（MPA）分析

- 日期：2026-10-19
- 关联需求：房间分享系统优化（链接邀请 / 扫码入房）
- 结论速览：**当前 SPA 已能满足链接邀请与扫码入房，无需迁移多页面；本文档仅作为未来若确有需求时的评估参考。**

## 1. 背景

房间分享需要「把房间地址发给队友 → 对方点开链接/扫码即可进入房间」。这类深链（deep link）
通常需要一个能承载「入口地址 → 具体页面状态」的路由能力。因此需要先判断：当前单页应用能否
承担邀请链接，若不能，是否值得迁移到多页面。

## 2. 当前前端架构事实

| 维度 | 现状 |
| --- | --- |
| 页面数量 | 单个 `dist/public/index.html`，由 `pages.py` 的 `/` 路由返回 |
| 静态路由 | `/<path:path>` 仅按文件是否存在返回静态资源；不存在则回退 `BASE_DIR`，仍不存在则 404 |
| 客户端路由 | 无路由库；主标签切换由 `tabs.ts` 的 `switchMainTab` 驱动，状态保存在 `window.*` 全局 |
| 脚本组织 | 各 `frontend/src/app/**/*.ts` 编译为全局脚本（`module: none`），通过全局对象/函数互相调用 |
| 实时通信 | 单一 Socket.IO 连接，加入房间后按 room 频道收发 |
| 构建 | `scripts/build-frontend.mjs` 拼装 HTML 片段 + `tsc` 编译 JS + `esbuild` 打包 React 局部 |

## 3. 邀请链接在 SPA 下的可行性结论

**可行，且已实现。** 采用查询参数形式：

```
http://<对外地址>:<端口>/?join=<房间码>
```

- `/` 路由始终返回同一份 `index.html`，查询参数由前端读取，不依赖服务端路由匹配，因此**无需**
  为深链新增服务端 fallback。
- 启动时 `rooms.ts` 的 `autoLoadLastRoom()` 优先解析 `?join=`，命中则填入房间码并进入加入流程；
  未登录时保留参数，登录后由 `restorePostLoginState()` 再次触发，实现「先登录再进房」。
- 二维码只是把同一条邀请链接编码渲染，扫码后浏览器打开同一 URL，天然复用该逻辑。

因此本次**不满足**迁移多页面的触发条件；若未来需要，才参考下文评估。

> 补充：唯一无法在 SPA 下直接支持的是「路径式」深链（如 `/join/ABC123`）。它需要给 `/<path:path>`
> 增加一条「未命中静态文件时回退返回 `index.html`」的兜底路由。这是一次很小的服务端改动
> （约 5 行），不属于迁移多页面的理由。

## 4. 若迁移多页面：好处

1. **深链与分享更直观**：每个功能有独立 URL（如 `/rooms`、`/scenarios/:id`），利于分享、直达与
   浏览器原生前进/后退。
2. **首屏更轻**：按页面拆分脚本，用户不必加载全部功能代码，弱网/移动端首屏更快。
3. **团队并行更友好**：页面边界清晰，减少多人同时改同一大文件（`rooms.ts` 等）的冲突。
4. **更利于 SEO 与外部集成**：真实 URL 便于被搜索/被第三方链接，也便于独立部署子应用。
5. **渐进式重构更容易**：可逐页迁移，避免「一次性重写」的风险集中。

## 5. 若迁移多页面：坏处 / 代价

1. **全局状态与单连接假设被打破**：当前大量状态存于 `window.*`、单 Socket 连接、`switchMainTab`。
   多页面意味着整页跳转，状态不保留；要么每次跳转重建连接（延迟与重复握手），要么引入持久化/
   共享层，改动面很大。
2. **构建与部署复杂度上升**：需要多入口构建、公共 chunk 抽取、静态路由与 fallback 规则维护。
3. **实时能力退化风险**：页面跳转会中断当前房间的实时推送，需重新设计「跨页面保持房间会话」。
4. **重复加载与体验回退**：相比 SPA 的瞬时切换，整页刷新会有白屏/闪烁，反而可能变慢。
5. **大量既有代码需要适配**：`tabs.ts`、`rooms.ts`、`chat.ts`、`auth/*`、React 局部等都要重新
   组织入口与导航；测试（前端结构测试、静态资源缓存测试）也要同步调整。
6. **收益相对有限**：本地/局域网部署场景对 SEO、首屏体积的敏感度低于公网 SaaS。

## 6. 风险

| 风险 | 说明 | 等级 |
| --- | --- | --- |
| 实时会话中断 | 房间内聊天/推送依赖长连接，跳页即断 | 高 |
| 回归范围大 | 触及导航、鉴权恢复、房间加入等核心链路 | 高 |
| 状态迁移遗漏 | `window.*` 全局状态散落，难以穷举 | 中高 |
| 构建/缓存回归 | 多入口产物与 `no-cache` 策略需重新校准 | 中 |
| 收益不明确 | 当前主要痛点（分享）已由 SPA 解决 | 中 |

## 7. 工作量与时间估算

（相对估算，仅供规模判断；实际取决于实时会话保持方案的选择。）

| 阶段 | 内容 | 相对工作量 | 粗估（人日） |
| --- | --- | --- | --- |
| 方案设计 | 路由方案、状态/连接保持策略、URL 规范 | S | 1–2 |
| 构建改造 | 多入口、公共 chunk、HTML 模板拆分 | M | 2–4 |
| 服务端路由 | 静态路由 + SPA fallback、缓存头调整 | S | 1–2 |
| 页面迁移 | 主标签拆分为页面、导航重写 | L | 5–10 |
| 实时会话 | 保持房间长连接/重连与状态恢复 | M–L | 3–6 |
| 鉴权/恢复 | 登录态恢复、深链回跳 | M | 2–3 |
| 回归与测试 | 前端结构/缓存测试改造、端到端手测 | M | 3–5 |
| **合计** | | **L** | **约 17–32 人日** |

对比：本次「SPA 内实现链接邀请 + 二维码 + 分享地址配置」的实际改动为 **S 级**（数小时量级，
仅少量前端文件与一个后端接口 + 一个校验），收益/成本比显著更优。

## 8. 若未来确需迁移的建议路径

1. 先只补一条 **SPA fallback 路由**（未命中静态文件时回退 `index.html`），即可支持路径式深链，
   成本极低，能覆盖多数「分享直达」诉求。
2. 若仍需多页面，采用**渐进式**策略：先抽公共构建与路由骨架，迁移风险最低的静态页
   （设置/帮助），再评估房间等实时页；实时页优先保留长连接或采用「子应用嵌入」而非整页跳转。
3. 全程保留现有 `switchMainTab` 入口作为兼容层，降低一次性回归风险。

## 9. 决策建议

- **现在：不迁移。** 邀请链接与扫码已在 SPA 内落地，多页面的收益不足以覆盖其风险与工作量。
- **触发迁移的条件（任一满足再启动）**：确需大量路径式深链且不愿只加 fallback；需要公网 SEO；
  首屏体积成为实测瓶颈；团队规模增长到单文件协作冲突难以管理。
